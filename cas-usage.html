D’une issue GitHub au déploiement

Le cas livré utilise GitHub, des worktrees, des candidats vérifiés et Docker Compose. Les étapes et leurs issues viennent de examples/code-task.json.

Admettre une tâche

Le canal graphatom github-sync --repo owner/repo --graph examples/code-task.json publie le graph et surveille les issues portant le label graphatom. GRAPHATOM_TAKE_ALL permet de prendre toutes les issues ouvertes. Le canal demande un accès GitHub configuré.

La plus ancienne issue admissible entre seule dans le rail. Les suivantes portent rail:queued et restent hors de PostgreSQL, sans bail ni deadline. L’item actif conserve la voie pendant la review.

Depends-on: #29 diffère l’admission jusqu’à la fermeture de la dépendance ; le label est rail:blocked. Retry-of: #172 peut reprendre les fichiers de critères, validation et échec d’un item terminal. Ce sont des règles du canal, pas une jointure entre items. Admission GitHub.

Le chemin nominal

NœudTravail et sortie
ingest → worktreeMatérialiser l’entrée puis créer le worktree de l’item.
scopeÉcrire les critères ; ready → implement, unclear → clarify, split → cleanup_split.
implement → judgeTrois candidats, portes propres à chaque candidat, keep_n avec n = 2, puis un élu.
test_backend → test_frontendCommandes de contrôle sur le travail retenu.
validate → reviewVérifier les critères et préparer la checklist ; pass ouvre la question humaine.
review → releaseL’option merger autorise la livraison ; abandonner mène au nettoyage non résolu.
release → deployLivrer le changement ; rebased retourne aux tests, conflict escalade.
deploy → verify_deployDéploiement sérialisé ; waiting revient sur deploy, puis vérification du résultat.
cleanup → closeRetirer les ressources de travail, puis terminer.

Le budget du profil est de cinq escalades et sa deadline globale de 72 heures. Les branches terminales sont close, close_unresolved et close_split. Toutes les commandes, prompts et arêtes.

Répondre à une question

La question est publiée sur l’issue avec ses options et son identifiant. Une personne autorisée par GRAPHATOM_ANSWERERS répond dans un commentaire dont la première ligne suit la forme /answer <id> <option>. Une explication peut suivre. Le serveur web et la CLI peuvent aussi enregistrer la réponse.

La review du rail propose merger ou abandonner. Une approbation de PR GitHub seule ne remplace pas cette réponse. La réponse est attribuée et stockée ; le worker effectue la transition. L’expiration de la review mène à l’escalade.

Le front présente le graph, les tentatives, la commande effective, les traces, les critères, la checklist et les liens vers l’issue et la PR lorsqu’elle existe. Réponses GitHub.

Quand une étape échoue

  • Critères incomplets : clarify propose go ou reformuler.
  • Aucun finaliste : judge revient à implement. Un échec de validation y revient aussi.
  • Échec de contrôle ou livraison en conflit : le graph ouvre escalate, avec retry ou abandon.
  • Déploiement occupé : deploy attend sur sa file ; l’attente n’est pas un échec.
  • Worker arrêté : les battements signalent l’arrêt. Les pages peuvent rester disponibles alors que les items ne progressent plus.

Les reprises restent bornées par le budget et la deadline. La trace d’échec conserve les informations de la tentative. Trace d’échec.

Le déploiement a deux périmètres

Le profil livre les services avec les scripts du dépôt et contrôle le déploiement. Le worker d’agents tourne sur l’hôte : un changement de son code demande une activation distincte, après le terminal de l’item. Le guide décrit l’arrêt de l’admission, l’alignement du checkout, le redémarrage du service et le contrôle de son battement.
