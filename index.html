Le noyau

Une machine à états persistante qui exécute des tâches isolées et externalise les effets de façon réconciliable. Six pièces, sept concepts pour l'utilisateur, et rien d'autre dans le noyau.

Ce qu'un utilisateur doit savoir

Sept concepts suffisent pour écrire et exécuter un premier graph :

ConceptDéfinition
nœudune étape typée : observer, juger, produire, agir sur le monde, attendre
entréeles artefacts qu'un nœud reçoit, référencés depuis un nœud précédent
issuece qu'un nœud peut répondre — un énuméré fermé, déclaré
arêteissue → nœud suivant ; chaque issue a exactement une arête
retryrejouer coûte un budget fini que rien ne régénère
deadlinetoute attente est bornée ; l'expiration est une issue comme une autre
effettoute action sur le monde extérieur passe par la passerelle, jamais en direct

Tout le reste — fencing, baux, réconciliation, gardes de frontière — est le travail du noyau, invisible tant qu'il ne se passe rien d'anormal.

Les six blocs livrés

Un bloc est du code qui implémente l'interface d'exécution du noyau ; le catalogue est ouvert. Six blocs sont livrés, et couvrent l'essentiel :

BlocCe qu'il faitCe qu'il n'a pas le droit de faire
FETCHlit le monde extérieur, matérialise des preuves (logs, pages, diffs) sur l'itemmodifier quoi que ce soit
JUDGEappel modèle : lit le contenu, répond dans l'énuméré fermé de son schémamodifier le contenu ; rejouable sans danger
ACTappel modèle : travaille dans un workspace isolé, publie un checkpoint validétoucher le monde extérieur ou son propre harnais (budgets, checks)
CHECKvérification déterministe — tests, lint, règles — verdict pass / failappeler un modèle ; c'est une porte, pas un avis
EFFECTremet une intention à la passerelle : ouvrir une PR, déployer, notifieragir lui-même ; seule la passerelle touche le monde
WAITattend une réponse humaine typée — responsable nommé, deadline obligatoireposer une question ouverte ; l'expiration est une issue routée

La colonne de droite n'est pas une consigne : elle est appliquée par l'isolement et la passerelle. Un ACT ne peut pas déployer, même si son modèle le veut.

Un exemple complet

graph supervision @rev 7c1f…            — immuable, adressée par contenu
  source      = failed_runs
  subject_key = [pipeline, error_class]
  budgets: escalations = 4, wall_deadline = 7d

  node ingest   : FETCH { materialize: [logs] }
      ok → diagnose
  node diagnose : JUDGE { schema: cause_v1 }
      → decide
  node decide   : JUDGE { schema: verdict_v1 }
      fix   → produce
      raise → escalate
      known → close
  node produce  : ACT   { workspace: isolated }
      ok → verify
  node verify   : CHECK { manifest: checks@3 }
      pass → commit
      fail → escalate
  node commit   : EFFECT { intent: open_change }
      applied   → close
      uncertain → escalate
  node escalate : WAIT  { owner: oncall, deadline: 4h }
      answered → decide
      expired  → close_unresolved
  node close, close_unresolved : terminal

Les issues mécaniques — crashed, timed_out, invalid_result, budget_exhausted — ont des défauts centralisés (réessayer, puis escalader ; épuisement → close_unresolved). Un graph ne les redéclare que pour les surcharger. Les références d'artefacts sont résolues par le runtime depuis le prédécesseur réel, puis enregistrées explicitement — l'auteur n'écrit jamais de qualificatif de tentative.

Les six pièces

1 · révision immuable

Un graph publié est une donnée adressée par contenu : nœuds, schémas, issues, arêtes. Item et run épinglent leur révision ; un résultat n'est jamais interprété par une autre.

2 · apply() unique

Toute mutation d'état d'un item passe par une seule fonction transactionnelle. L'identité vient de la ligne chargée, jamais de l'appelant ; un rejet (stale, superseded) est lui-même une transition durable.

3 · issues fermées

Chaque nœud déclare son énuméré ; chaque issue a exactement une arête ; une issue non mappée est une faute. Rien d'autre ne route — pas de conversation, pas d'exception.

4 · passerelle d'effets

Intention et clé logique commises avant tout accès au monde. États : applied / rejected / uncertain / possibly_sent. « Inconnu » est un état de première classe, réconcilié en interrogeant la cible.

5 · baux et fencing

Chaque run tient un bail ; l'expiration révoque l'autorité (annulation, terminaison, quarantaine du workspace), pas seulement l'acceptation du résultat. Le jeton se compare par égalité.

6 · terminaison

Sous-graph non-escalade acyclique + budget d'escalade fini que rien ne régénère + deadlines partout ⇒ tout item termine. C'est la garantie qui distingue un rail d'un tableau de suivi. Les tentatives par nœud sont un autre compteur : un amortisseur local, remis à zéro pour le passage qu'ouvre un retry humain — jamais le budget d'escalade.

apply(run_id, submitted):
  atomically:
    run  ← node_run[run_id] FOR UPDATE       — l'identité vient de la ligne
    item ← work_item[run.item_id] FOR UPDATE
    if run.fence ≠ item.fence                → record(superseded); return
    if run.expected_version ≠ item.version   → record(stale); return
    outcome ← validate(submitted, run.schema) or KERNEL(invalid_result)
    edge ← transitions[item.revision, item.state, run.node, outcome]
    guard_boundaries(edge)                    — voir les quatre gardes
    append_event ; item.state ← edge.target ; item.version += 1
    enqueue_intents(edge.effects)             — exécutés hors txn, par la passerelle

Le cycle de vie d'un nœud

Comment un item change de nœud — validé par le crash-test du milestone 1. Trois temps, dont un seul hors transaction :

TempsTransactionnel ?Ce qui se passe
claim()ouiRéservation : un run est créé, le fence de l'item est incrémenté, la version courante est épinglée (expected_version), un bail est posé. Refusé si l'item est terminal, en WAIT, ou déjà réservé.
exécution du blocnonLe bloc travaille dans son workspace, aussi longtemps que le bail tient. Il peut crasher, ralentir, être tué : rien de ce qu'il fait n'engage l'item.
apply(résultat)ouiValidation de l'issue, comparaison fence/version, routage par l'arête déclarée, version += 1, événement journalisé. Un rejet (superseded, stale) est classé sur le run, l'item n'a pas bougé.

Trois déclencheurs, et seulement trois, font bouger un item : le résultat d'un run (apply), une réponse humaine ou une deadline (apply_item — transition sans run), et le faucheur (bail expiré → fence incrémenté, run classé faulted, issue crashed routée comme n'importe quelle autre). Une question de WAIT est armée dans la même transaction que l'entrée dans l'état WAIT — pas de réveil perdu possible. Tuer l'ordonnanceur en plein vol traverse ce cycle sans le casser : c'est un cas nominal, pas une panne.

Les quatre gardes de frontière

Un item est étanche à l'intérieur ; les incidents réels arrivent aux frontières — le temps, les autres items, les gens, sa propre lignée. Quatre gardes, chacune rangée là où elle s'exécute :

GardeOù elle s'exécuteViolationLe bug évité
fraîcheurapply(), à la reprise après un WAITstaledécision prise lundi sur la v42, exécutée vendredi alors que le monde est en v45
version de cible (If-Match)passerelle d'effets, à l'émissionconflictdeux items écrivent la même cible, deux « applied ✓ », l'un a écrasé l'autre en silence
capacité humainepublication du graphunbackedun graph réserve l'équipe sécurité sans son accord → rubber-stamp ou expiration de masse
budget de lignéeadmission d'une occurrenceexhausteditem épuisé → clôture → ré-admission du même sujet avec un budget neuf, à l'infini

Deux règles complètent les gardes. Un constat d'opérateur — « j'ai vérifié la cible, voici son état » — est un événement journalisé de première classe, jamais un UPDATE direct : c'est la seule façon de lever un uncertain. Et aucun nœud d'observation ne peut lire la base du runner lui-même — c'est une jointure déguisée, refusée à la validation.

La persistance

graph_revision(id, content_hash, bundle)
subject(id, graph, subject_key, lineage_budget, UNIQUE(graph, subject_key))
work_item(id, subject_id, generation, revision, state, version, fence,
          cycle, UNIQUE(subject_id, generation))
node_run(id, item_id, node, cycle, attempt, status, fence, expected_version,
         lease_expires_at, outcome, result_ref,
         UNIQUE(item_id, node, cycle, attempt))
event(item_id, item_version, edge, run_id, PRIMARY KEY(item_id, item_version))

       intent_hash, observation, UNIQUE(target_uri, logical_key))
artifact(id, sha256, bytes, media_type)

Sept tables. Le subject est durable, le work_item en est une occurrence numérotée — la déduplication est une politique explicite, pas un effet de bord d'un index. Rien de volumineux en base : les artefacts vivent dans un magasin adressé par contenu.

Honnêteté sur la garantie

Pas d'exactement-une-fois

La passerelle fournit l'au-moins-une-fois avec réconciliation, et l'idempotence effective seulement quand la cible sait dédupliquer par clé. Là où elle ne le sait pas, la réponse honnête est un état ambigu visible et une reprise en main humaine — pas une promesse.

Ce que la déclaration est vraiment

Ce n'est pas un langage de workflow : le comportement vit dans les blocs, les schémas et les gestionnaires d'effets — du code. La déclaration est de la configuration au-dessus d'une interface de blocs typée. Elle reste défendable à une condition : rester étroite. Le jour où on y ajoute expressions et conditions arbitraires, un vrai programme typé aurait été supérieur.

Périmètre d'apply()

L'unicité d'apply() porte sur les mutations d'état d'un item. La réservation d'un run et la réconciliation d'un effet sont des transactions périphériques — mais toutes aboutissent à une transition apply(), et aucune ne route un item par un autre chemin.

Hors du noyau — les modules

Quatre sous-systèmes utiles, volontairement exclus du noyau. Chacun se branche sur le journal et les issues fermées ; aucun n'ajoute de concept au chemin d'entrée.

  • EVAL — mesure comparative, registre champion/challenger, distillation d'un juge coûteux en check déterministe.
  • ADMIT — la porte d'admission pour le travail formulé par un humain : faits vérifiables plutôt que score de clarté.
  • Dialogue durable — questions adressables, réponses typées, révisions immuables.
  • Gouverneur de flotte — contre-pression, jitter sur les échéances, garde-fou du reaper : la congestion est un état de flotte, pas un échec d'item.

Le raisonnement qui a conduit à cette forme — particules, forces d'interaction, douze trous de frontière — vit dans archive/graph-runner-original.html. C'est la dérivation, pas la spécification.
