GraphAtom · état du dépôt · 8 septembre 2026

Le système actuel

Un noyau Python et PostgreSQL pour exécuter des tâches d’agents, conserver leurs résultats et attendre des décisions humaines. Le dépôt fournit aussi un cycle GitHub de développement, une API et un front Next.js.

Ce qui fonctionne aujourd’hui

GraphAtom exécute un graph JSON publié sous une révision immuable. Un item garde un seul état ; plusieurs candidats peuvent travailler sur le même nœud. Le cycle fourni va d’une issue GitHub à la vérification du déploiement.

Le site que vous lisez est une documentation statique. Les vues des items, les questions et les traces sont dans l’application lancée avec le dépôt.

Démarrer avec un graph de démonstration

Prérequis : Git, Python 3.12 ou plus, uv et Docker. Depuis un clone du dépôt, lancer un PostgreSQL local dédié, puis publier l’exemple fourni. Cet exemple utilise des blocs simulés ; il ne demande aucun modèle.

git clone https://github.com/Acid3croco/graphatom.git
cd graphatom
docker run -d --name graphatom-docs-pg \
  -e POSTGRES_USER=graphatom -e POSTGRES_PASSWORD=graphatom \
  -e POSTGRES_DB=graphatom -p 127.0.0.1:54321:5432 postgres:17
# Attendre que cette commande indique que PostgreSQL accepte les connexions.
docker exec graphatom-docs-pg pg_isready -U graphatom
export GRAPHATOM_DSN=postgresql://graphatom:graphatom@127.0.0.1:54321/graphatom
uv run graphatom init-db
REV=$(uv run graphatom publish examples/supervision.json)
uv run graphatom admit "$REV" "demo:premier-essai"
uv run graphatom run

Dans un autre terminal du même clone, avec le même GRAPHATOM_DSN, lancer uv run graphatom serve, puis ouvrir http://127.0.0.1:8848. Le worker doit rester actif pour faire avancer les items.

uv run graphatom items
uv run graphatom questions
uv run graphatom journal <item_id>
uv run graphatom answer <question_id> retry

Remplacer les identifiants par ceux affichés. Répondre seulement avec une option de la question ouverte. Arrêter le worker et le serveur avec Ctrl-C. Exemple complet · Commandes CLI.

La déclaration est du JSON

Le format lu par graphatom publish contient name, entry, budgets, on_kernel et nodes. Les clés de edges définissent les issues du domaine. Un terminal porte terminal: true.

{
  "name": "premier-graph",
  "entry": "verify",
  "budgets": {
    "escalations": 2,
    "wall_deadline_hours": 1
  },
  "on_kernel": {
    "escalate_to": "ask",
    "exhausted_to": "unresolved"
  },
  "nodes": {
    "verify": {
      "block": "CHECK",
      "edges": {
        "pass": "done",
        "fail": "ask"
      }
    },
    "ask": {
      "block": "WAIT",
      "escalade": true,
      "config": {
        "question": "Retenter ou abandonner ?",
        "options": [
          "retry",
          "abandon"
        ],
        "owner": "operator",
        "deadline_minutes": 10
      },
      "edges": {
        "retry": "verify",
        "abandon": "unresolved",
        "expired": "unresolved"
      }
    },
    "done": {
      "terminal": true
    },
    "unresolved": {
      "terminal": true
    }
  }
}

Enregistrer ce JSON dans un fichier, puis le publier avec uv run graphatom publish <fichier.json>. Ce CHECK sans exécution configurée est une simulation qui répond pass. Un contrôle réel déclare config.execution.

La publication refuse notamment les cibles absentes, les nœuds inatteignables, les cycles hors escalade et les WAIT sans options ou arête expired. Une file déclarée par file: true peut avoir une arête vers elle-même. Validation.

Les six types de blocs

TypeImplémentation actuelle
FETCHMatérialisation simulée de preuves dans le workspace.
JUDGERéponse simulée, exécution configurée, ou sélection de finalistes.
ACTCheckpoint simulé ou exécution configurée dans le workspace.
CHECKVerdict simulé ou exécution configurée pour produire une issue de contrôle.
EFFECTDémonstration de réconciliation avec une outbox locale et une intention en base.
WAITQuestion durable armée par le noyau ; réponse ou expiration traitée par le worker.

ACT, CHECK et JUDGE acceptent une exécution agent ou command. Le type du bloc ne constitue pas une sandbox de sécurité. Blocs livrés.

Les règles du noyau

  • Révision immuable. Le SHA-256 du bundle canonique identifie le graph publié. L’item reste sur sa révision.
  • Transitions transactionnelles. Le noyau réserve un run, exécute hors transaction, puis contrôle son fence, sa version et son résultat. Résultats, réponses et expirations utilisent le routage commun et le journal.
  • Issues fermées. Le résultat doit nommer une issue déclarée. Les erreurs mécaniques suivent on_kernel.
  • Baux. Un résultat révoqué ne peut plus déplacer l’item. Le faucheur et les groupes de processus prennent en charge les runs orphelins.
  • Budgets distincts. Le défaut est de trois tentatives par nœud et passage. Une réponse humaine sur un nœud d’escalade ouvre un nouveau passage. Le budget d’escalades ne se régénère pas ; une re-entrée le consomme, pas la première visite du passage. La deadline globale reste fixe.
  • Erreurs classées. crashed, invalid_result et stalled peuvent être retentés ; une panne déterministe répétée peut supprimer cette relance. timed_out et starved escaladent immédiatement.

La boucle d’une file, comme deploy, attend une ressource sans consommer d’escalade ; elle reste bornée par la deadline globale. Ces bornes sont traitées quand le worker tourne. Noyau · Routage · Faucheur.

Agents, commandes et candidats

Le contrat explicite est config.execution.kind : agent pour une CLI de modèle, command pour du shell. Une commande déclare execution.cmd. Un agent déclare config.agent.prompt et hérite séparément de la CLI, du modèle et de l’effort du graph. Les adaptateurs livrés sont Claude, Codex et OpenCode.

L’agent reçoit prompt.md. Toute exécution produit outcome.json dans son workspace ; c’est son issue qui route, pas le code de sortie shell. usage.json est facultatif. Les agents laissent une passation, sauf désactivation explicite. La commande effective, les logs et les événements restent consultables par tentative.

Le fan-out multiplie les candidats d’un même nœud, sans créer plusieurs états d’item. La borne est de huit candidats. Dans code-task, trois variantes courent : Luna medium, Sol high et OpenCode avec le modèle gratuit configuré. keep_n garde au plus deux finalistes ; judge choisit un élu. Un seul finaliste ne demande pas d’appel de jugement.

Les candidats ont leurs worktrees et leurs preuves. Leurs résultats sont réduits avant le passage au nœud suivant. Les CLI et leurs accès doivent être installés sur l’hôte du worker ; les noms de modèles sont des réglages du bundle. Profil actuel · Exécuteurs · Réduction.

À ces huit tables durables s’ajoute database_incarnation, une table UNLOGGED qui aide à détecter une reprise PostgreSQL après crash. Les fichiers vivent dans data/item-<id>/ et les worktrees ; il n’y a pas de table artifact ni de magasin générique adressé par contenu. Schéma complet.

Application et limites de charge

Le Compose fournit PostgreSQL 17, la migration init, github-sync, le serveur web et le front Next.js. Le worker de vrais agents tourne sur l’hôte ; le scheduler conteneurisé est réservé au profil stub. Le front est accessible localement sur 8851, le canal web de secours sur 8850 et PostgreSQL sur 54322.

Pour les agents, configurer GRAPHATOM_AGENT_DSN vers une instance où le rôle peut créer les bases jetables par item, et GRAPHATOM_REPO_DIR vers le clone de référence. Le guide détaille aussi le jeton GitHub, GRAPHATOM_ANSWERERS, le proxy et l’activation du worker. Reconstruire les conteneurs ne recharge pas le Python du worker hôte. Compose · Guide d’exploitation.

Une seule occurrence non terminale occupe la voie, y compris pendant la review. Les autres issues admissibles attendent sur GitHub. Les plafonds des runs valent par défaut max(8, cœurs // 2) au total et max(8, plafond // 2) par item ; GRAPHATOM_MAX_RUNS et GRAPHATOM_MAX_RUNS_PER_ITEM les remplacent. Une course est réservée entière ou attend.

Les commandes lourdes utilisent graphatom build-quota -- <commande> : max(1, cœurs // 6) places par défaut, réglables par GRAPHATOM_MAX_BUILDS. Les verrous PostgreSQL de session rendent les places à la déconnexion ; l’attente conserve le bail.

Vérifier le dépôt

uv run python scripts/check.py        # train + core
uv run python scripts/check.py train  # noyau, pannes et cycle complet
uv run python scripts/check.py core   # preuves sans service partagé
uv run python scripts/check.py ui     # build Next.js et portes DOM
uv run python scripts/check.py full   # base, crash, concurrence, Docker
uv run python scripts/check.py live   # vraie CLI OpenCode et réseau
uv run python scripts/check.py rules  # qualité et couverture

Le runner vérifie que chaque test est classé et s’arrête au premier échec. train utilise un PostgreSQL Docker jetable. ui demande Node.js et npm ; la CI utilise Node 22. full ne remplace pas les autres groupes : les arguments sont composables. GitHub Actions lance train, core, ui et rules séparément.

rules exige notamment 100 % de couverture des lignes et branches Python, des fichiers de moins de 500 lignes, des complexités cyclomatique et cognitive inférieures à 22, et un CRAP inférieur à 25. Ce sont des seuils à mesurer, pas une preuve de réussite de chaque révision.

Ce qui reste une intention de conception

Le noyau contrôle les transitions. Il ne fournit pas une sandbox qui interdit à toute commande d’agir sur le réseau ou le dépôt. La livraison GitHub et le déploiement utilisent aussi des scripts spécialisés ; toute action externe ne passe donc pas par un gestionnaire EFFECT universel.

Le schéma permet uncertain et le canal GitHub réconcilie ses commentaires. Il n’existe pas encore de contrat général If-Match, de contrôle générique de fraîcheur après WAIT, de réservation de capacité humaine, ni de commande universelle de constat d’opérateur.

Notion, Coolify, EVAL, la distillation et un gouverneur de flotte ne sont pas des intégrations livrées. La découpe générale reste une conception ; le cycle GitHub dispose déjà de Depends-on: et split-close. Lire les choix et limites.
